## 1. Category A — Proposed Runtime Software Dependency Policy

### 1.1 Permitted Runtime License Families (Proposed)

Under Laqta's permanent **MIT License** model (`v0.2.5+`), runtime software dependencies (packages imported at runtime in Python or bundled into built frontend assets) are proposed to be limited to:

- `MIT`
- `Apache-2.0`
- `BSD` variants (`BSD-2-Clause`, `BSD-3-Clause`, `0BSD`)
- `ISC`
- `Unlicense`
- `MPL-2.0`
- `PSF-2.0`
- `BlueOak-1.0.0`
- `MIT-0`

_(Additional permissive component licenses encountered inside vetted scientific wheels — specifically `Zlib`, `CC0-1.0`, and `NCSA` inside `numpy` — are flagged in Section 4.1 for explicit exception or inclusion.)_

### 1.2 Copyleft & Dual-License Boundaries

1. **Third-Party Dependency Licenses Stay Separate From Laqta MIT Source:** Using or combining an `MPL-2.0`-licensed third-party runtime dependency (such as `certifi` or `tqdm` files) in an application bundle or container does **not** relicense Laqta's own independent MIT source files (`MPL-2.0 §3.3` Larger Works), nor does a third-party `MPL-2.0` package alter Laqta's first-party MIT grant. Upstream `MPL-2.0` notices and source-availability rules still apply to those third-party files themselves if redistributed.
2. **Strong Copyleft Runtime Prohibition:** **GPL** (`GPL-2.0`, `GPL-3.0`) and **AGPL** (`AGPL-3.0`) runtime dependencies remain **prohibited** unless the maintainer explicitly approves an isolated exception following legal review (notably for bundled PyAV/FFmpeg shared libraries in any future container or installer artifact).

## 2. Category B — Proposed Build, Test, and Development Dependency Policy

Build, lint, formatting, security-audit, benchmark, and test tools (`devDependencies` in `frontend/package.json` and `[dev]`/`[test]` in `pyproject.toml`) are governed separately from shipped runtime libraries:

1. **Development-Time vs. Redistribution Boundary:** Installing a tool in CI or on a developer workstation does **not** inject its license into Laqta's source tree or Vite's compiled JS output (`frontend/dist/`). However, **dev-only status does NOT make a tool's license irrelevant if the tool itself, `node_modules`, or a dev container containing that tool is redistributed** (for example, publishing a dev container image or archival build bundle).
2. **Tool-Specific Rules Under Category B:**
   - **`MPL-2.0` Build Tools** (`lightningcss@1.33.0`, nested `@1.32.0`, and optional platform binaries): Permitted for CSS bundling/transpilation at build time; must **never** be bundled into `frontend/dist/` runtime output or source tarballs. If a container layer retaining `node_modules` is ever distributed, MPL-2.0 §3.1–§3.2 source notice obligations apply to `lightningcss`.
   - **`PSF-2.0` / `PSFL` Tooling** (`defusedxml==0.7.1` in `pip-audit` tree): Permitted for security auditing and CI checks; preserve PSFL notice if dev environments are redistributed.
   - **`BlueOak-1.0.0` Tooling** (`minimatch@10.2.6`): Permitted across ESLint/Vitest/build dependency trees; retain license notice if `node_modules` is redistributed.
   - **`MIT-0` Tooling** (`@csstools/color-helpers@5.1.0`): Permitted across CSS build tooling with zero runtime output inclusion.
   - **GPL Development/Benchmark Tools (`espeak-ng` — GPL-3.0):** Invoked as an external CLI subprocess by benchmark and clean-room verification scripts (`scripts/verify_release.py`, `scripts/verify_release.sh`, `scripts/evaluate_ranking.py`, `backend/tools/benchmark_transcription.py`) and installed ephemerally in CI (`.github/workflows/release-check.yml`, `evaluation.yml`). Permitted **strictly as an unbundled external dev/CI CLI**; must **never** be bundled into release archives, runtime Docker images (`Dockerfile`), or desktop installers unless full GPL-3.0 compliance (corresponding source + notices) is explicitly approved.

## 3. Category C — Datasets, Lookup Tables & Non-Code Content Assets

Creative Commons Attribution licenses (`CC-BY-4.0`) and content licenses govern data/documentation works differently from software code and should **not** be grouped under Category A software licenses:

1. **Separated Governance:** Any external dataset, lookup table, caption sample, audio corpus, or reference file under `CC-BY-4.0` (or similar content license) requires a per-asset clearance record **before** entering the repository or any distributed build.
2. **Mandatory Clearance & Distribution Requirements for Content Assets:**
   - **Source Identification:** Exact canonical URL, publisher, dataset version, and retrieval date.
   - **Attribution Text:** Exact attribution block satisfying CC-BY-4.0 §3(a)(1) (creator name, copyright/attribution notice, license notice, disclaimer of warranties, URI).
   - **License Link:** Official license URI (e.g., `https://creativecommons.org/licenses/by/4.0/`).
   - **Indication of Modifications:** Explicit log of whether and how data was filtered, subsetted, formatted, or translated (CC-BY-4.0 §3(a)(1)(B)).
   - **Redistribution Permission Review:** Verify whether the license contains `-NC` (NonCommercial) or `-ND` (NoDerivatives) restrictions (both incompatible with open-source distribution) and confirm whether compiled release bundles actually ship the data or only read it at build time.
   - **Unverified Provenance Prohibition:** Files lacking verifiable source/license provenance (such as the removed historical Arabic broadcast caption track) remain strictly forbidden.
